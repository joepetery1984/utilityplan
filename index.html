1. Arsitektur Ekosistem & Model Bisnis Lintas Layanan

Sistem ini dirancang menggunakan arsitektur Enterprise di mana utilitympro.com bertindak sebagai Satu Portal Utama (Kredit Redeem). Setelah pengguna top-up, mereka dapat menggunakannya di berbagai layanan anak yang memiliki Role Model Pembayaran masing-masing:

  • mpro-video.com (Layanan AI Video) - Sistem: Pay-per-use (Contoh: 1 Video = 10 Kredit)
  • mproaitrade.utilitympro.com (Layanan AI Trading Athena) - Sistem: Langganan (Subscription) (Mingguan / Bulanan)
  • dracin.utilitympro.com (Layanan Dracin) - (Coming Soon)
  • token.utilitympro.com (Layanan API Token) - (Coming Soon)

2. Manajemen Kredit, Wallet, & Komitmen Burning (Deflasi)

Portal menggunakan sistem Top-Up untuk menghindari Gas Fee berulang. Berikut adalah aturan utama (Tersimpan di SQL DB):

  • Harga Kredit Dinamis: Konversi MPRO ke Kredit (Harga Kredit) disetting murni dari dalam SQL DB, sehingga perusahaan bisa mengubah rasio konversi kapan saja tanpa mengubah Smart Contract.
  • Wallet Penampung Dinamis: Alamat Wallet Penampung tidak di-hardcode, melainkan dipanggil dari DB berdasarkan proyek. (Misal: Pembayaran untuk `mpro-video` akan dirouting ke Wallet A, sedangkan langganan masuk ke Wallet B).
  • Mekanisme Burning (Death Wallet): Sebagai bentuk komitmen MPRO Ecosystem untuk menaikkan harga token, setelah MPRO masuk, Backend Sistem akan secara otomatis mengirimkan alokasi persentase tertentu ke Wallet Death (Alamat Burn) di Blockchain.

3. Integrasi Trust Wallet (WalletConnect)

Mengingat target audiens menggunakan Trust Wallet di perangkat mobile (HP), pendekatan teknis terbaik di sisi Frontend adalah menggunakan protokol WalletConnect (AppKit), bukan sekadar deteksi MetaMask (window.ethereum) seperti sebelumnya.

Alurnya: Pengguna menekan tombol, muncul QR Code (di desktop) atau opsi "Open in Trust Wallet" (di HP/Deep Linking), dan menyetujui transaksi deposit langsung di aplikasi Trust Wallet mereka.

5. Penjelasan Alur (Sesuai DFD)

Fase 1: Proses Top-Up (Redeem) & Mekanisme Burn

Pengguna masuk ke portal utilitympro.com. Saat akan Top-Up, sistem membaca Harga Kredit dan Wallet Penampung dari SQL Database. Pengguna mentransfer MPRO via Trust Wallet. Setelah sukses, Backend akan menambahkan Kredit Internal ke SQL DB. Bersamaan dengan itu, Backend akan mengeksekusi transfer dari Wallet Penampung (di BSC) menuju Dead Wallet sebagai bentuk komitmen Burning Token secara otomatis.

Fase 2: Penggunaan Layanan Berdasarkan Role Model (Off-Chain)

Kredit yang telah masuk ke SQL DB dapat digunakan lintas ekosistem (SSO):

  • Sistem Pay-per-use (mpro-video.com): Pengguna meminta layanan sekali pakai (contoh: Generate Video). Backend mengecek saldo, memotong 10 Kredit, memproses render AI, dan mengirimkan video.
  • Sistem Langganan (mproaitrade.utilitympro.com): Pengguna membeli paket akses mingguan/bulanan. Backend memotong sejumlah kredit besar sekaligus dan mengubah flag (status) akses pengguna di SQL DB menjadi "Aktif" hingga masa berlakunya habis.

8. Arsitektur Database & Usulan Tabel Baru

Berdasarkan skema saat ini (4 tabel: users, service, transactions, settings), berikut adalah pemetaan fungsionalnya dan usulan penambahan untuk mendukung fitur Email, Referral, dan Langganan:

Tabel Eksisting (Perlu Penyesuaian)

  • users: Saat ini menyimpan identitas Web3 (wallet_address). Usulan: Tambahkan kolom email (varchar) untuk notifikasi/marketing, dan pastikan USER_REFFERAL digunakan untuk mencatat siapa yang mengundang user ini.
  • service: Menyimpan daftar layanan dan harga. Usulan: Tambahkan kolom wallet_receiver (varchar) di tabel ini. Ini berfungsi sebagai "Wallet Penampung Dinamis" yang akan dipanggil saat Top-Up / transaksi masuk, seperti yang kita bahas sebelumnya.
  • transactions: Menyimpan riwayat Top-Up, Burn, dan Penggunaan Kredit.
  • settings: Untuk konfigurasi global sistem (seperti parameter/rasio burn).

Tabel Baru yang Dibutuhkan

  • user_subscriptions: Sangat penting untuk Model Langganan (Sistem 2 - mproaitrade). Tabel `transactions` saja tidak cukup untuk mengecek apakah langganan masih aktif atau sudah habis masa berlakunya.
    Kolom: id, wallet_address, service_id, start_date, expired_date, status.
  • referral_history (Opsional): Jika sistem referral memberikan bonus kredit saat downline melakukan transaksi, Anda butuh tabel ini untuk mencatat log pembagian komisi agar tidak terjadi double-claim.
    Kolom: id, referrer_wallet, referred_wallet, bonus_kredit, created_at.
